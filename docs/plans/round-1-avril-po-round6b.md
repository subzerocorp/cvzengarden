## ZG-21 — Publish a résumé to a stable public URL with an unguessable edit link (API)

**What changed, in Author terms.** Delete now has one meaning instead of two. Before, the body said the row is removed and also that the public link answers 410 forever; an implementer had to pick, and the cheapest pick (a hidden flag with the résumé kept) would have made ZG-22's "Kept until you delete it" a lie for exactly the people who pressed Delete. Now: DELETE erases the résumé bytes and the key hash, leaves a tombstone (`id`, `theme_id`, timestamps, `deleted_at`), the public link answers 410 "This résumé was taken down." forever, and the id is never reissued. Three smaller folds ride along: an unmatched path or wrong verb under `/api/` gets the same plain JSON error body as everything else (405 `method-not-allowed` is the seventh code), a missing `theme` gets the same 422 a wrong one gets with a sentence naming `theme`, and the 1 MiB limit is measured on bytes received so a chunked upload cannot slip past it.

**Does it keep Marcus's and Priya's promises true?** It makes them true. Marcus #2 asked for "a stated retention policy for anonymous pastes, a one-click delete, and export of the JSON I gave you". After this revise, delete means the résumé is gone from the row — provably, since `delete_then_gone` reads the row back by SQL — and export is available right up to the moment he deletes (ZG-22's "Download my JSON" works from the edit link; the chrome confirms before it deletes). Priya #4 asked for "Delete anytime here" and "who can see this". The 410 is the better answer for her than a vanished 404: a recruiter who saved her link learns it was taken down on purpose, not that they mistyped it. And "never reissued" is a promise a removed-row design could not make: with random ids there is no way to say that her old link will never, ever show somebody else's résumé; with a reserved tombstone there is. That is the one sentence in this revise that an Author would notice if it were missing.

**ZG-22's copy, line by line, against the new semantics.** "Only people with the link can see it — it is not listed or indexed": unchanged, and the 410 carries the same `no-store` / `noindex` headers. "Kept until you delete it": now structurally true — after DELETE, `resume_json IS NULL`. "Your JSON stays yours; download it any time": true while the page exists; after delete the export path is 404 because there is no résumé and no key hash to compare, and the Author has already confirmed once in the chrome. The privacy panel's "what the server stores: the JSON, the theme, timestamps" describes a live page and stays true; on a tombstone the JSON is gone and what remains (a catalog theme id, timestamps, a dead link) is not the Author's résumé and not personal. ZG-22 needs no edit, as the Generator verified, and I confirm its `delete`, `wrong-key` and `api-errors` probes are all satisfied by this body. One wording thought for the human who owns decision 5, not a blocker and not this item: the panel could say in one clause that after delete only the dead link is kept so it can never show anyone else's page. That is a stronger trust sentence than the product had before this revise, and it is available for free.

**A stale edit link after delete.** Second DELETE, PUT with the old key, export with the old key are all 404. From the Author's chair this is invisible in the normal flow (ZG-22 clears `localStorage` after the 204) and, if an old edit link is reopened, the chrome shows its plain `edit-denied` state — no cryptic error, nothing resurrected, existence never revealed. Consistent with "we cannot recover it" in ZG-22's copy.

**The three folds, as product.** None of them is a new outcome and none is reachable from ZG-22's chrome (it sends the right verbs and always sends `theme`). Their value is that the promise the body already made — "every non-2xx under `/api/` is `{error, message}` in plain words" — no longer has a hole in it, and the size limit that protects the store (and the Turso bill, human decision 8) cannot be bypassed. One probe case each, no new endpoint, no new field. The Generator chose a seventh code over "405 is exempt"; I agree — an exemption would have been the first asterisk on a promise whose whole point is having none.

**Non-goals, honest.** `Scope out` is unchanged and still refuses accounts, slugs, retention automation, stored HTML, CORS, deploy and field-level validation. The `deleted_at` column is exactly the seam a later retention rule would query, but the item does not add one — no Phase 5 crept in, and lock 10 holds.

**Size.** Seven lines altered, none added or removed; the item is the same shape it was in cycle 5. Still the largest item in the set, still one shippable outcome (a résumé gets a URL it can lose on purpose), and the seam if the CTO calls size is unchanged: static serving + `just serve` + `missing_dist_is_a_clear_error`, never key handling, 404-not-403, or the delete semantics.

**Human decisions.** Unchanged: `sha2` / `rand` approval, and the retention wording — which this revise makes defensible as proposed. Ask both before AXEL starts the item.

**BLESS ZG-21 — the tombstone-and-erase delete is the thinnest slice that makes "Kept until you delete it", "Delete anytime" and "your link never shows anyone else's page" all true at once, and it does so with one column and one SQL assertion rather than a retention feature; the 405, `theme`-absent and bytes-received folds close holes in promises the body already made without adding an endpoint, a field or anything an Author sees; ZG-22's copy needs no edit and becomes true instead of asserted.**

## ZG-13 — Self-host first-party theme fonts so a résumé page never calls jsDelivr

**Themes stay files.** The fonts land as files under `themes/fonts/<family>/` with each family's `OFL.txt`, and the only "build" is `copy-dist.mjs` copying the directory into `dist/themes/fonts/` — the same one static root both `serve.mjs` and the Axum process serve (cycle-1 ruling on ZG-14). No bundler, no subsetting pipeline, no font-loading JavaScript; a Designer who clones the repo and opens `skeleton/example.html` against `../themes/quarto.css` gets the faces from disk because `url("fonts/…")` resolves relative to the sheet. That relative form is the strategically important choice: it is correct from disk, on Netlify, on the Axum static root, and on `/r/{id}` pages that link `/themes/{theme}.css` — four deployment shapes, one URL. `local("…")` first keeps a developer's installed faces and `fonts-load`'s `status !== 'error'` clause stops that convenience from hiding a broken `url()`.

**"A Theme is one `.css` file" stays true for contributors.** Fonts are neither JavaScript nor HTML, so lock 3 is untouched; the README sentence ("any https origin, self-hosted preferred; self-host in their PR") leaves both paths open and does not promise self-hosting beyond the PR path. That matters for the two-year shape: a Store-backed Submission later is one CSS file plus, at most, an https origin — it will not need an asset-upload surface, and the README will not have promised one. ZG-20's `url-origin` warning only on non-https absolute origins is consistent with this.

**No re-baseline, no reflow.** The body forbids touching `U3_PRINT_PAGES` / `LONG_PRINT_PAGES` and sends a reflow back to planning instead of to the constants — exactly the "re-baselined exactly once, by ZG-11" rule I set in cycle 1. The vendored binaries (~10 woff2) are the first binary assets in the repo; small, OFL-licensed, and a human approval in `notes`. Reversible (delete the directory, restore the `url()`), so not entanglement.

Guidance for AXEL: the request-log, font-file and `FontFace` helpers belong in `frontend/scripts/probes/lib/fonts.mjs` (execution rule 6), not inline in `probes.mjs`; resolve `url()`s relative to the sheet's URL, as QA noted, so a future `themes/<vendor>/x.css` needs no change. ZG-13 and ZG-19 both edit `themes/README.md` with no edge between them (different sections); land ZG-13 first, and when ZG-19 makes §2 the canonical fonts sentence, the README line may point at §2 the way the `content:` rule does.

**BLESS ZG-13 — fonts become files beside the Themes with relative URLs that are correct in all four serving shapes, no build step and no loader script, while the contributor rule keeps a Theme one `.css` file and leaves the later Submission store nothing to host.**

## ZG-17 — Add the repo LICENSE and state the theme-contribution license terms

**Reversible and consistent.** One `LICENSE` (MIT), `renderer/Cargo.toml` aligned to `MIT`, first-party headers already `MIT`, contributed Themes MIT or CC BY 4.0. Collapsing Cargo's `MIT OR Apache-2.0` to `MIT` is a one-token change in each direction for a `publish = false` crate with one contributor; if the crate is ever published to crates.io the ecosystem's dual-license convention (the Apache patent grant) can be restored then. The window in which that reversal stays trivial closes as contributors arrive — which is precisely why the ZG-17 → ZG-18 edge (terms before the submit path) is the right ordering and must be kept.

**The human decision is surfaced.** `notes` names both choices (copyright holder; MIT-only vs dual) and calls each a one-line change. My only precision: "dual" is two files (`LICENSE-MIT` and `LICENSE-APACHE`) and two AC tokens (`test -f LICENSE`, `license = "MIT"`), still trivial, still planning-time. It is batched below as decision 2.

**The commercial-hosting right is the strategic content.** Refusing CC BY-NC-* and stating that the Garden may host Themes on free and paid pages is what lock 8 (hosted page + print is the paid product) requires; without it every accepted Theme is a latent dispute. Limiting the attribution promise to the credit that ships (the ZG-16 switcher byline) keeps the terms honest, and the hosted-page byline remains an open seam (ZG-21's purity AC admits an HTML comment) rather than a promise. The static probe that guards the README section against the two downstream editors is the right kind of lock: a policy that cannot be un-said by accident.

**BLESS ZG-17 — a single MIT stance that is reversible while the contributor set is small, ordered ahead of the submit path so the reversal window is respected, with the commercial-hosting right and the BY-NC refusal that the paid product depends on and a human decision that is named, batched, and one-line.**

## ZG-21 — Publish a résumé to a stable public URL with an unguessable edit link (API)

**Stratification is mandated, not merely permitted.** `Scope in` states the layering I asked for in cycle 1: pure `domain` (ids, the ordered validation with the section-key shape check, render-with-theme), `store` (libSQL actions), `http` (handlers), with `thiserror` errors mapped to status + `{error, message}` in one place. The store is one implementation selected by environment — `libsql` local file / `:memory:` by default, `TURSO_DATABASE_URL` + `TURSO_AUTH_TOKEN` switch to Turso "with no code change" — which is lock 7 without a second adapter. The "test store wrapper" that counts calls implies a `Store` trait with a counting decorator in tests; that is the seam, and it is the only place a second implementation belongs. Render on read from the verbatim JSON of record is in `scope_out` as a refusal to store HTML. No CORS layer keeps the deploy topology a human decision. `clippy::pedantic` and `grep -rn anyhow` empty are gates, not hopes.

**URL space and identity model hold for two years.** `/r/{id}` with a 10-char base32 id from 50 random bits is a namespaced, unguessable, never-reused public URL; `/api/`, `/themes/`, `/skeleton/` are separate prefixes, so vanity slugs later can take `/{slug}` or `/u/{slug}` without touching `/r/`. The edit key is a bearer capability: returned once, stored as a SHA-256 hash, accepted only in `Authorization`, wrong or absent key is 404 (existence never revealed). Accounts later *claim* a row by presenting the key once and `resumes` gains an `account_id`; nothing in the table, the routes or the fragment scheme (ZG-22) has to be replaced. The ordered validation contract (413 → 400 → 422 with a pure shape check, then the crate as the final oracle, row written only after `render_json` succeeded) is the same twelve-line rule as ZG-5's Elm check with the same vectors — the tolerable duplication I accepted in cycle 1 with a named exit (export the crate's check through the Wasm module).

**What is missing, and why it is strategic.** The body says two incompatible things about the one irreversible operation in the data model. `Scope in`: "`DELETE` removes the row." Also `Scope in` and `delete_then_gone`: after DELETE, `GET /r/{id}` is `410 … taken down` (and a second DELETE, or a PUT with the old key, is 404). A removed row cannot answer 410 — the id would be indistinguishable from one never issued. So the execution team must invent the delete semantic, and the schema it is given (`resumes(id, edit_key_hash, theme_id, resume_json, created_at, updated_at)`) has no column for it. The cheapest invention is a soft-delete flag with `resume_json` kept — which makes ZG-22's privacy panel ("what the server stores: the JSON, the theme, timestamps" / "kept until you delete it") false the day a page is deleted, and it is the semantic that cannot be corrected after deployment (bytes kept cannot be un-kept for the users who already deleted). The right semantic is the one that makes both the 410 and the trust copy structurally true: a tombstone that reserves the id forever and erases the résumé bytes and the key hash. It is also the seam Phase-5 retention automation will build on (`deleted_at`), so pulling it forward loses no option value. This is a data-lifecycle rule, not a test-mechanics nit; it belongs in the body, not in AXEL guidance, because the DoD checks ACs.

**Exact sentence to add** (replacing "`DELETE` removes the row" in `Scope in`, and the schema gains `deleted_at`):

> `DELETE` erases the résumé and keeps a tombstone: it sets `resume_json` and `edit_key_hash` to NULL and `deleted_at` to now (the table gains a nullable `deleted_at`), leaving the `id` row in place so `GET /r/{id}` answers 410 forever and an id is never reissued; a direct SQL read of the row after DELETE finds no résumé bytes and no key hash.

Suggested AC shape for the Generator (QA owns the final wording): `delete_then_gone` additionally reads the row by SQL after the 204 and asserts `resume_json IS NULL`, `edit_key_hash IS NULL`, `deleted_at IS NOT NULL`; `edit_key_not_stored_plain` is unaffected. ZG-22 needs no edit — its `delete` probe (410 + `taken down`) and its privacy copy are satisfied, and become true rather than merely asserted. QA's three non-blocking folds (unmatched `/api/` routes and 405 shape, `theme` absent, 413 by bytes received) can ride the same revise.

Guidance for AXEL (not blocking): one crate, three modules (`domain`, `store`, `http`); the `Store` trait has exactly one production impl over `libsql::Database` built by `Builder::new_local` or `Builder::new_remote` from env, plus a counting decorator in tests; randomness is an action at the handler edge (`rand`/`getrandom`, decision 4) and `id_from_bits`, `hash_key`, `key_matches` (constant-time over 32 bytes, std only) are pure functions in `domain` with unit tests; three error enums (`DomainError`, `StoreError`, `ApiError`) with `From` impls and a single `IntoResponse`; the theme catalog for `unknown-theme` is the `dist/themes/*.css` listing minus `_blank.css` read at startup — Themes are files, never a Rust array (a third catalog beside `generate.mjs` and the lint is a reject at code review); `render_document(resume, theme_id) -> String` is the one place the `<link>` is inserted after `<title>`, so a later byline comment or `<meta>` has one seam; expose `CONTRACT_VERSION` and `version()` on a response header or `/api/version` (execution rule 8, zero cost, additive); handle a primary-key collision on insert by retrying the random draw, not by erroring.

**REJECT ZG-21 — layering, single env-selected store, capability edit key, stable `/r/{id}` space and render-on-read are all right and mandated, but the body says both "DELETE removes the row" and "after DELETE, 410 forever", leaving the execution team to invent the one irreversible data-lifecycle rule with a schema that has no place for it; replace the removal sentence with the tombstone-and-erase sentence quoted above (`resume_json` and `edit_key_hash` NULL, `deleted_at` set, id reserved) and let `delete_then_gone` read the row — one sentence, one column, one assertion, and ZG-22's trust copy becomes structurally true.**
